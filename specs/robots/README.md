# Robot and configuration profiles, revision 0.1.0

Copyright 2026 Living Proof Labs contributors. [CC BY 4.0](../../LICENSES/CC-BY-4.0.txt).

This document defines how a robot, the configurations it can run with, and one
run of a scenario are described. Terms are defined in the
[glossary](../../docs/glossary.md). A worked example is the
[hallway walk](../scenarios/walk-hallway/README.md) with the Unitree G1.

## Three facts kept apart

A scenario says **what is asked**, a robot repository says **who is asked**, and
acceptance says **what is good enough**. Keeping them in separate versioned files
lets one scenario serve several robots, and several configurations of one robot,
without copying numbers into the scenario.

| File | Says | Owned by | Schema |
| --- | --- | --- | --- |
| Robot profile, `robot.json` | Identity, class, dimensions, pinned model, offered configuration names, declared simulators | The robot repository (`livingproof-<manufacturer>-<model>`, or a partner's downstream repository) | [robot-profile.schema.json](robot-profile.schema.json) |
| Configuration profile, `configurations/<name>.json` | One named, versioned configuration: controller, gains, limits, anything else | The robot repository | [configuration-profile.schema.json](configuration-profile.schema.json) |
| Run manifest | What one run used | Generated by the simulator runner; never committed | [run-manifest.schema.json](run-manifest.schema.json) |
| Robot manifest | What a robot repository offers a verifier: configurations, adapter entry point, pinned assets with sha256, feature flags, per-simulator compatibility | The robot repository | [robot-manifest.schema.json](robot-manifest.schema.json) |
| Scenario and acceptance | The story, steps, metrics and thresholds | This catalog, under `specs/scenarios/` | Markdown and Gherkin |

## Configuration profiles

A configuration profile is the general unit of variation within a robot. Two
profiles may differ by controller, by proportional-derivative gains, by limits,
or by anything else the robot implementation needs; the format does not try to
list every possibility.

- **Named by the robot repository.** The name tells a reader what the big change
  is, such as `stock` or `playground`. The robot repository is responsible for
  keeping each name matched to its details.
- **Versioned and hashed.** Any change to a profile's contents, even one gain,
  changes its sha256 and needs a new version.
- **Referenced, not copied.** Specifications and run manifests use only the
  profile name, version and sha256 of the profile file bytes as committed.
  The difference between two profile files explains a change between two runs.
- **The controller is one property.** The `controller` object pins the published
  artifact by commit and sha256. `settings` is free-form for everything else.
- **The feature toggle selects a profile.** The run manifest's `configuration`
  field is the toggle; exactly one profile is selected per run. Selecting a name
  the robot profile does not offer gives `UNSUPPORTED` naming
  `configuration_offered` before any trial.

## Partner robots downstream

A partner keeps its robot repository, configuration profiles and specifications
in its own hosting under its own licence, mirrored downstream. Its files validate
against the public schemas but need not be public. The run manifest records the
robot repository commit, the robot profile sha256 and the configuration profile
sha256, so the hashes prove exactly what ran.

## Run manifest

The runner writes the manifest before the first trial and keeps it with the
evidence. Every input is pinned: specification tag and commit, scenario, world
and its sha256, simulator and adapter commit, robot repository commit and profile
sha256, the selected configuration profile, resolved parameters, and seeds. Two
runs can be compared only when their manifests differ in the declared field.

## Grades

A run gets a **grade**; one trial gets a **trial outcome** (`PASS`, `FAIL` or
`ERROR`).

| Grade | Meaning | Decided |
| --- | --- | --- |
| `PASS` | The acceptance rule is met | After trials |
| `FAIL` | Trials ran and the rule is not met | After trials |
| `INSUFFICIENT_EVIDENCE` | Required metrics or files are missing, or too many trials ended in `ERROR` | After trials |
| `UNSUPPORTED` | A declared precondition cannot be met; names the precondition | Before any trial |
| `ERROR` | The run could not be completed | Any time |

## Robot manifest

A robot manifest (`livingproof-robot-manifest/0.1`) gathers, in one file, what a
generic runner and the verifier need from a robot repository. It cites the robot
profile and each configuration profile by path and sha256 instead of copying them.

- `adapter.entry_point` is the `module:object` a generic runner loads (the
  `[tool.livingproof] adapter` value in `pyproject.toml`).
- `assets` lists every upstream file with its repository, commit, sha256 and size,
  as fetched and checked from `pins.json`; nothing is vendored.
- `features` are boolean flags; a missing flag means false.
- `simulators` is optional: per simulator, the engine version, the runner release
  and a status of `verified`, `experimental` or `unsupported`.

[Example manifests](examples/manifests/) for the Unitree G1, Unitree Go1 and
Booster T1 are built from those repositories' `robot.json`,
`verification.lock.json`, `pins.json` and `pyproject.toml`. Check any manifest
with `task validate:manifests -- path/to/manifest.json`.
